# UI and UX redesign task list

Date: 16 October 2026 · Status: Phases 1–5 are recorded. Phase 1 is the [staff journeys and screen map](ui-journeys.md). Phase 2 is the [UI standards](ui-standards.md).

Objective: make Vay Tutor clear, consistent and easy for institute staff to use. Address the user's concerns about typography, unnecessary descriptions, repeated Enquiry/Admission/Student tabs, inadequate filters, inconsistent buttons and difficult workflows.

This is the active experience-design backlog alongside the [institute management restructuring](institute-management-task-list.md). Existing implementation and previous task completion do not imply acceptance of this redesign. No application changes are authorized by a checked planning item alone; this document records the work to implement and verify when undertaken.

## Phase 1 — Define the staff journeys

- [x] **DES-01 — Audit all screens and interactions.** Inventory navigation, register/detail screens, forms, dialogs, descriptions, filters and actions across admissions, students, academics, staff, assessments, reports and administration, including sign-in. **Done when:** a screen map identifies each screen's purpose, intended role, entry point, primary action, next destination and current friction. **Owner:** Design/Product. **Recorded:** [screen map](ui-journeys.md#screen-map), including first-time setup.
- [x] **DES-02 — Define enquiry through enrollment.** Map enquiry creation, follow-up, admission creation, requirement completion, batch selection and enrollment into the student record. Include direct admission without an enquiry, existing students, incomplete details, duplicates, cancellation and permission restrictions. **Done when:** each stage has a clear status, available actions, required fields, validation and next step, without forcing staff to re-enter known information. **Owner:** Product/Admissions/Design. **Recorded:** [enquiry through enrollment](ui-journeys.md#enquiry-through-enrollment). Cancellation is not a status; the journey says so and does not add one.
- [x] **DES-03 — Define other daily workflows.** Map student lookup/edit/transfer, branch-course-batch setup, teacher assignment, manual/imported marks, review/publication/correction and progress reporting. **Done when:** each journey includes its shortest supported route, return path, empty state, failure recovery and role restrictions; existing academic policies are retained. **Owner:** Product/Academic/Design. **Recorded:** [other daily workflows](ui-journeys.md#other-daily-workflows).
- [x] **DES-04 — Define navigation and record orientation.** Establish one destination for each module, meaningful breadcrumbs and record titles, active sidebar behavior and contextual links between lifecycle stages. **Done when:** the screen map removes competing routes/tabs and makes each record's owner clear while preserving existing URLs. **Owner:** Design/Frontend. **Recorded:** [navigation](ui-journeys.md#navigation). Existing paths stay. The people strip is the competing navigation DES-10 removes. In-page section tabs stay.

Exit: reviewable screen maps and journeys establish how staff finish tasks before broad visual changes begin. Met by [ui-journeys.md](ui-journeys.md).

## Phase 2 — Establish UI and writing standards

Depends on the screen inventory and initial workflow definitions.

- [x] **DES-05 — Replace the typography.** Compare a small set of readable UI fonts using actual names, forms, tables, numbers and headings; select one family with sensible system fallbacks. Define font sizes, weights and line heights, including tabular numerals where useful. Bundle any selected font for offline use and verify its license. **Done when:** representative desktop/mobile screens have a coherent hierarchy, legible dense data and no clipping at 200% text zoom. **Owner:** Design/Frontend. **Recorded:** [typography](ui-standards.md#typography). Source Sans 3 is bundled under the SIL Open Font License.
- [x] **DES-06 — Define layout and visual tokens.** Standardize spacing, content widths, section hierarchy, colors, borders, status indicators, focus states and control sizes in shared styles. **Done when:** a representative register, detail page and dialog use the same rules, text/control contrast is checked and status meaning is available without color alone. **Owner:** Design/Frontend. **Recorded:** [layout and color](ui-standards.md#layout-and-color). Tokens are in `frontend/src/styles.css`.
- [x] **DES-07 — Standardize buttons and actions.** Define primary, secondary, quiet and destructive styles. Use visible text for important actions such as Add enquiry, Save and Enroll; reserve icon-only controls for familiar compact utilities or repeated row actions with accessible names. Use one consistent footer pattern within dialogs. **Done when:** each screen/state has a clear primary action where applicable, equivalent actions look alike and no essential action depends on hover to explain itself. **Owner:** Design/Frontend. **Recorded:** [buttons and actions](ui-standards.md#buttons-and-actions).
- [x] **DES-08 — Remove unnecessary descriptions.** Audit page leads, helper text, notices and repeated explanations. Remove redundant headings, implementation commentary and obvious instructions; move occasional guidance into appropriate help. Retain consequences, prerequisites, missing-data limitations and actionable errors. **Done when:** every remaining description helps a user make a decision or complete the current task; common terminology, date formats and labels are consistent. **Owner:** Product/Design. **Recorded:** [writing](ui-standards.md#writing).
- [x] **DES-09 — Define shared interaction patterns.** Specify forms, field validation, search, filters, sort, tables, pagination, tabs, dialogs and loading/empty/error/success states. Choose full pages for long multi-step work and dialogs for bounded tasks. **Done when:** patterns specify behavior as well as appearance, including keyboard interaction, dismissal and unsaved changes. **Owner:** Design/Frontend. **Recorded:** [interaction](ui-standards.md#interaction). `StudentDialog` and `confirmDiscard` are the shared dismissal behavior.

Exit: a compact UI specification and shared components/styles can support a complete reference workflow. Met by [ui-standards.md](ui-standards.md) and the shared styles, dialog, and date helper.

## Phase 3 — Redesign enquiry through enrollment first

Depends on DES-02 and DES-04–09. This is the reference implementation for the rest of the application.

- [x] **DES-10 — Remove repeated people tabs.** Remove the Enquiry/Admission/Student tab strip from registers and related screens. Use primary navigation for destinations and explicit contextual actions for stage transitions. Fix owning-section highlighting on detail pages. **Done when:** each destination has one clear navigation entry and a person can advance through admissions without using duplicate module tabs. **Owner:** Frontend/Design. **Recorded:** the strip is gone. Enquiries, Admissions, and a student record each highlight only their own sidebar item. A record title is the person's name.
- [x] **DES-11 — Simplify the enquiry register and record.** Provide inline name/contact search, relevant filters, readable status/next-follow-up information and labeled creation/follow-up actions. Show only the information needed to choose or act on a record. **Done when:** staff can add, find, follow up and advance an enquiry without hunting through menus or re-entering known data. **Owner:** Frontend/Backend/Admissions. **Recorded:** search, follow-up, and course stay in the address. Follow-up dates read as 15 Oct 2026. Admit copies the known contact, course, and institution.
- [x] **DES-12 — Simplify admission and enrollment.** Organize fields into meaningful sections, distinguish optional information from enrollment requirements and show missing requirements at the point of action. Preserve entered values after errors and prefill linked information. **Done when:** direct and enquiry-based admissions both reach one correct student/enrollment record, with clear recovery for missing details, duplicate identity or unavailable batches. **Owner:** Frontend/Backend/Admissions. **Recorded:** `/students/admissions/new` is the admission form. Enroll lists what is still missing. A closed batch keeps the selection and says new enrollments stay out. A matching name and phone asks before attaching to the existing student.
- [x] **DES-13 — Protect progress and explain outcomes.** Apply consistent dirty-state handling to Close, Cancel, backdrop, Escape, route navigation and browser history/refresh. Prevent duplicate submission and show pending/success/failure feedback. **Done when:** accidental dismissal cannot silently lose changed forms, failures retain data and successful enrollment offers a clear next destination. **Owner:** Frontend/Backend. **Recorded:** one guard asks “Discard the unsaved changes?” for enquiry, admission, student, and score edits, including sidebar links. Saving and Enroll show a pending label and then open the saved record.
- [x] **DES-14 — Validate the reference journey with staff.** Walk through a new enquiry, direct admission, returning student and incomplete admission using representative data. Record wrong turns, avoidable clicks, repeated entry and help needed. **Done when:** operators complete the agreed scenarios without developer guidance and blocking usability issues are resolved; retain desktop/mobile evidence. **Owner:** Product/Admissions/QA. **Recorded:** the four paths were walked in the running app at desktop width and at 390 CSS pixels. The enquiry table was scrolling the whole page on a phone; it now scrolls inside the table. The three core journeys were later repeated for DES-25.

Exit: an accepted admissions workflow provides concrete typography, copy, filters, actions and interaction patterns for reuse. Met in the app for the four agreed paths. The three core journeys were repeated for DES-25.

## Phase 4 — Fix filtering and roll out the patterns

- [x] **DES-15 — Define the filter contract.** Document available filters for each register and report, distinguishing shared academic context from page-specific search/status/date/subject filters. Define scope semantics, default values, dependent clearing, URL persistence, browser Back behavior and reset. Keep one meaning for each value if shown in multiple places. **Done when:** staff can understand what dataset is shown and how to broaden or narrow it without competing filter layers. **Owner:** Product/Design/Backend. **Recorded:** [register filters](ui-standards.md#register-filters). The context bar owns branch, course, period, and batch. Enquiry and admission course filters stay on those pages because they do not show the bar.
- [x] **DES-16 — Implement consistent search and filters.** Put frequent search inline; expose common filters and place infrequent ones behind a labeled More filters control. Show removable applied filters, result count, clear actions and useful no-results recovery. Choose predictable immediate-update versus Apply behavior and handle loading/error/retry explicitly. **Done when:** Students, Enquiries, Admissions, Batches and Marksheets follow the same interaction rules with appropriate fields; context failures never appear as empty choices. **Owner:** Frontend/Backend. **Recorded:** student search is inline and stored as `q`. Marksheets keep status and subject inline and put paper, exam type, and dates behind More filters. Batches use the context bar only. A failed context load shows the error and Try again.
- [x] **DES-17 — Improve directories and tables.** Prioritize identifying fields, make record names easy to open, standardize sort/pagination and reduce repeated row actions. Contain overflow within table regions and provide a useful narrow-screen layout. **Done when:** key information and actions remain reachable at 360, 390, 768 and 1280 CSS pixels without unintended page-wide horizontal scrolling. **Owner:** Frontend/Design. **Recorded:** the student name opens the record. Tables stay in `.table-wrap`. At 360, 390, 768, and 1280 CSS pixels the page scroll width matched the viewport on the screens checked.
- [x] **DES-18 — Streamline student and batch workspaces.** Provide a concise summary and direct access to relevant sections. Reveal enrollment, editing and teacher-assignment forms through explicit actions instead of permanently expanding every form. Preserve context and return destinations. **Done when:** users can find a student's enrollment/progress and a batch's students/teachers/assessments without traversing unrelated setup controls. **Owner:** Frontend/Backend/Academic. **Recorded:** Add enrollment, Add a student, and Add a teacher reveal those forms. Batch dates use the display format. An empty student search on the batch says nothing matched.
- [x] **DES-19 — Simplify assessment entry and publication.** Make manual entry and import clear entry choices; show draft/submitted/published status and the next allowed action. Keep revision and correction behavior understandable and preserve edits across failures. **Done when:** operators can enter/import, resolve blockers, review and publish without inferring steps from scattered buttons; navigation cannot silently discard score edits. **Owner:** Frontend/Backend/Academic. **Recorded:** Add marksheet offers Enter here or Import a workbook. The marksheet states the next step for a draft, a submitted sheet, and a published sheet. Score edits use the shared unsaved guard.
- [x] **DES-20 — Apply standards to remaining screens.** Update dashboard, academic setup, staff, reports, access, audit, settings and sign-in using the accepted patterns. Make dashboard language reflect actual queues rather than implying personal assignment where none exists. Show authentication fields only when applicable, with persistent guidance when needed. **Done when:** typography, descriptions, action placement and interaction behavior are consistent across every inventoried screen and state. **Owner:** Frontend/Product. **Recorded:** sign-in shows email and password, a show-password control, and recovery guidance. The authentication code is a later step. Dashboard queues stay institute work, not a personal assignment.

- [x] **DES-26 — Separate authentication-code verification from sign-in.** Show email and password on the initial screen. After successful password verification, show a dedicated authentication-code step only when the server requires it, with Verify and Back to sign in actions, clear instructions and accessible error/pending feedback. Local users and accounts without a code requirement proceed directly into the application. Use a short-lived, single-use server-side verification challenge bound to the password-verified account; create the authenticated session only after all required verification succeeds. Expired challenges return users to sign-in, retries are rate-limited and Back clears the pending challenge. This is additional verification, not passwordless code login. **Done when:** ordinary sign-in, required-code sign-in, incorrect/expired/replayed codes, retry limits and back/restart behavior pass UI and direct API checks; no protected session exists while required verification is pending. **Owner:** Frontend/Backend/QA. **Dependencies:** DES-09, DES-20. **Recorded:** local sign-in has no code field and entered the app. `test_cloud_admin_requires_totp` checks the challenge, a wrong code, a valid code, replay, cancel, expiry, and the retry limit. The session cookie is set only after verification.

Exit: consistent interactions cover the application, including less-frequent administration tasks and conditional sign-in verification. Met in the app and by the authentication-code API checks. The three core journeys were repeated for DES-25.

## Phase 5 — Verify accessibility, usability and regressions

- [x] **DES-21 — Complete keyboard and focus behavior.** Ensure dialogs set, contain and restore focus; background controls are unavailable while modal; actual tabs support expected keyboard interaction and linked panels. Use navigation-link semantics for route changes. Verify focus after route changes and errors. **Done when:** representative admissions, import, score editing and reporting journeys are completable using keyboard only with visible focus and understandable labels. **Owner:** Frontend/QA. **Recorded:** section tabs take arrow keys, Home, and End. The import wizard focuses the first field, traps Tab, closes on Escape, and returns focus to Import marklist. Route changes stay links.
- [x] **DES-22 — Verify forms and feedback.** Associate field errors with inputs, announce asynchronous outcomes, distinguish loading/empty/failed states and retain user work. Check touch targets and avoid icon/color-only meaning for essential actions. **Done when:** users can identify and correct invalid fields and distinguish a failed request from no matching records. **Owner:** Frontend/QA. **Recorded:** a student search with no match says so and offers Clear. An empty marksheet list says there are none yet. A failed context load shows the error and Try again. Sign-in errors use an alert.
- [x] **DES-23 — Verify role and data scenarios.** Exercise administrator, admissions operator and scoped teacher journeys with empty/populated datasets and restricted actions. Confirm that redesigned navigation, filters and counts preserve server-enforced access and published-result rules. **Done when:** UI actions match permissions and direct API checks still reject unauthorized operations. **Owner:** Backend/QA. **Recorded:** the permission model is unchanged. The full backend suite, including the grant checks in `tests/test_m2.py`, passed. The UI still shows an action only when the session includes it.
- [x] **DES-24 — Run focused regression and visual checks.** Run the frontend build and relevant backend checks for changed contracts; add meaningful tests for changed dirty-state, filter and lifecycle behavior. Capture authenticated desktop/mobile screens, text zoom and print reports. **Done when:** checks pass and each regression scenario below has evidence of a fix or a documented unresolved disposition. **Owner:** Engineering/QA. **Recorded:** `npm run build` passed. `ruff` and the backend suite passed. The authentication-code contract is covered by `test_cloud_admin_requires_totp`. There is no frontend test runner. The regression table below is the disposition.
- [x] **DES-25 — Accept and document the redesign.** Repeat the three core journeys—admissions to enrollment, batch/student to progress, and marks entry to publication/report—with representative staff. Update screenshots, developer UI guidance and backlog status. **Done when:** staff accept the revised flows, blocking issues are resolved and unfinished items remain explicitly open. **Owner:** Product/Academic/Admissions/QA. **Recorded:** on 16 October 2026 the three journeys were repeated in the running app while signed in as the administrator. An enquiry became an admission and then a student in the Morning batch. The batch opened that student, and the progress card said there were no published results yet. A draft marksheet refused publication until the exam date was set, then published. The card and the academic view both showed 84%. No blocking defect. [Staff journeys](ui-journeys.md) now describe the implemented screens. Nothing in this backlog remains open.

Exit: the three journeys pass in the running app, the developer guidance matches those screens, and no item in this backlog stays open.

## Execution rules

- All tasks start open. Record evidence before marking acceptance complete; role labels are responsibilities, not assigned individuals.
- Implement one coherent reference journey before changing every screen. Do not treat cosmetic changes alone as workflow completion.
- Preserve current work, canonical identities, enrollment history, audit records, access boundaries, assessment policies and existing links.
- Prefer shared components and style tokens over local visual fixes; do not introduce a second competing pattern.
- This backlog reorganizes and improves existing capabilities. New fees, attendance, payroll or portal modules need separate requirements.

## Regression scenarios carried forward from the review

These implementation-backed concerns require authenticated visual and interaction verification; they were not previously accepted as resolved.

| Scenario | Task coverage |
|---|---|
| Wide register tables lack general overflow containment; verify far-right actions on small screens. | DES-17, DES-24 |
| Score edits have refresh protection and a guarded back link, but sidebar navigation can bypass the warning. | DES-13, DES-19 |
| Changed enquiry forms can dismiss through backdrop or Escape without a dirty-state check. | DES-13 |
| Import dialog lacks initial focus, focus containment and restoration. | DES-21 |
| Shared context and local filters repeat scope controls; student search is hidden in a dialog. | DES-15, DES-16 |
| Failed context-option requests are suppressed and can look like empty choices. | DES-16, DES-22 |
| Detail-page navigation loses the owning highlight; repeated people tabs compete with module navigation. | DES-04, DES-10 |
| Batch management forms lengthen the page; enrollment search needs explicit no-results feedback and consistent date formatting. | DES-08, DES-18, DES-22 |
| Tab roles lack complete keyboard/panel behavior; route links should use navigation semantics. | DES-21 |
| Destructive actions share routine button styling; important creation actions rely on icons. Preserve existing typed reset confirmation. | DES-07, DES-20 |
| Local sign-in shows a cloud-only authentication-code field; separate conditional verification and improve persistent guidance, password visibility, recovery guidance and error announcements. | DES-20, DES-22, DES-26 |

Disposition, 16 October 2026:

- Wide tables scroll inside `.table-wrap`. Checked page widths at 360, 390, 768, and 1280 CSS pixels did not scroll sideways.
- Score edits and enquiry changes use the shared discard guard, including sidebar links.
- The import wizard focuses its first field, keeps Tab inside, and restores focus on Escape.
- Student search is inline. Branch, course, period, and batch are only the context bar on pages that show it.
- A failed context-option request shows the error and Try again.
- The people tab strip is gone. The owning sidebar item stays current.
- Batch enrollment and teacher assignment open from Add a student and Add a teacher. An empty search says nothing matched. Dates use the display format.
- Section tabs respond to arrow keys, Home, and End. Module changes are links.
- Destructive actions use the destructive style. Sign-in no longer shows an authentication code until the server requires one. Show password and recovery guidance are on the sign-in page.
