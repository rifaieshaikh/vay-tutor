# UI and UX redesign task list

Date: 16 October 2026 · Status: Phases 1–6 are recorded. DES-41 is closed on the requester’s acceptance. Phase 1 is the [staff journeys and screen map](ui-journeys.md). Phase 2 is the [UI standards](ui-standards.md).

Objective: make Vay Tutor clear, consistent and easy for institute staff to use. Address the user's concerns about typography, unnecessary descriptions, repeated Enquiry/Admission/Student tabs, inadequate filters, inconsistent buttons and difficult workflows.

This is the active experience-design backlog alongside the [institute management restructuring](institute-management-task-list.md). Existing implementation and previous task completion do not imply acceptance of this redesign. No application changes are authorized by a checked planning item alone; this document records the work to implement and verify when undertaken.

## Phase 1 — Define the staff journeys

- [x] **DES-01 — Audit all screens and interactions.** Inventory navigation, register/detail screens, forms, dialogs, descriptions, filters and actions across admissions, students, academics, staff, assessments, reports and administration, including sign-in. **Done when:** a screen map identifies each screen's purpose, intended role, entry point, primary action, next destination and current friction. **Owner:** Design/Product. **Recorded:** [screen map](ui-journeys.md#screen-map), including first-time setup.
- [x] **DES-02 — Define enquiry through enrollment.** Map enquiry creation, follow-up, admission creation, requirement completion, batch selection and enrollment into the student record. Include direct admission without an enquiry, existing students, incomplete details, duplicates, cancellation and permission restrictions. **Done when:** each stage has a clear status, available actions, required fields, validation and next step, without forcing staff to re-enter known information. **Owner:** Product/Admissions/Design. **Recorded:** [enquiry through enrollment](ui-journeys.md#enquiry-through-enrollment). Cancellation is not a status; the journey says so and does not add one.
- [x] **DES-03 — Define other daily workflows.** Map student lookup/edit/transfer, branch-course-batch setup, teacher assignment, manual/imported marks, review/publication/correction and progress reporting. **Done when:** each journey includes its shortest supported route, return path, empty state, failure recovery and role restrictions; existing academic policies are retained. **Owner:** Product/Academic/Design. **Recorded:** [other daily workflows](ui-journeys.md#other-daily-workflows).
- [x] **DES-04 — Define navigation and record orientation.** Establish one destination for each module, meaningful breadcrumbs and record titles, active sidebar behavior and contextual links between lifecycle stages. **Done when:** the screen map removes competing routes/tabs and makes each record's owner clear while preserving existing URLs. **Owner:** Design/Frontend. **Recorded:** [navigation](ui-journeys.md#navigation). Existing paths stay. The people strip is the competing navigation DES-10 removes. In-page section tabs stay.

Exit: reviewable screen maps and journeys establish how staff finish tasks before broad visual changes begin. Met by [ui-journeys.md](ui-journeys.md).

## Phase 2 — Establish UI and writing standards

Depends on the screen inventory and initial workflow definitions.

- [x] **DES-05 — Replace the typography.** Compare a small set of readable UI fonts using actual names, forms, tables, numbers and headings; select one family with sensible system fallbacks. Define font sizes, weights and line heights, including tabular numerals where useful. Bundle any selected font for offline use and verify its license. **Done when:** representative desktop/mobile screens have a coherent hierarchy, legible dense data and no clipping at 200% text zoom. **Owner:** Design/Frontend. **Recorded:** [typography](ui-standards.md#typography). Source Sans 3 is bundled under the SIL Open Font License.
- [x] **DES-06 — Define layout and visual tokens.** Standardize spacing, content widths, section hierarchy, colors, borders, status indicators, focus states and control sizes in shared styles. **Done when:** a representative register, detail page and dialog use the same rules, text/control contrast is checked and status meaning is available without color alone. **Owner:** Design/Frontend. **Recorded:** [layout and color](ui-standards.md#layout-and-color). Tokens are in `frontend/src/styles.css`.
- [x] **DES-07 — Standardize buttons and actions.** Define primary, secondary, quiet and destructive styles. Use visible text for important actions such as Add enquiry, Save and Enroll; reserve icon-only controls for familiar compact utilities or repeated row actions with accessible names. Use one consistent footer pattern within dialogs. **Done when:** each screen/state has a clear primary action where applicable, equivalent actions look alike and no essential action depends on hover to explain itself. **Owner:** Design/Frontend. **Recorded:** [buttons and actions](ui-standards.md#buttons-and-actions).
- [x] **DES-08 — Remove unnecessary descriptions.** Audit page leads, helper text, notices and repeated explanations. Remove redundant headings, implementation commentary and obvious instructions; move occasional guidance into appropriate help. Retain consequences, prerequisites, missing-data limitations and actionable errors. **Done when:** every remaining description helps a user make a decision or complete the current task; common terminology, date formats and labels are consistent. **Owner:** Product/Design. **Recorded:** [writing](ui-standards.md#writing).
- [x] **DES-09 — Define shared interaction patterns.** Specify forms, field validation, search, filters, sort, tables, pagination, tabs, dialogs and loading/empty/error/success states. Choose full pages for long multi-step work and dialogs for bounded tasks. **Done when:** patterns specify behavior as well as appearance, including keyboard interaction, dismissal and unsaved changes. **Owner:** Design/Frontend. **Recorded:** [interaction](ui-standards.md#interaction). `StudentDialog` and `confirmDiscard` are the shared dismissal behavior.

Exit: a compact UI specification and shared components/styles can support a complete reference workflow. Met by [ui-standards.md](ui-standards.md) and the shared styles, dialog, and date helper.

## Phase 4 — Fix filtering and roll out the patterns

- [x] **DES-17 — Improve directories and tables.** Prioritize identifying fields, make record names easy to open, standardize sort/pagination and reduce repeated row actions. - [x] **DES-18 — Streamline student and batch workspaces.** Provide a concise summary and direct access to relevant sections. - [x] **DES-19 — Simplify assessment entry and publication.** Make manual entry and import clear entry choices; show draft/submitted/published status and the next allowed action. - [x] **DES-20 — Apply standards to remaining screens.** Update dashboard, academic setup, staff, reports, access, audit, settings and sign-in using the accepted patterns. Make dashboard language reflect actual queues rather than implying personal assignment where none exists. Show authentication fields only when applicable, with persistent guidance when needed. **Done when:** typography, descriptions, action placement and interaction behavior are consistent across every inventoried screen and state. **Owner:** Frontend/Product. **Recorded:** sign-in shows email and password, a show-password control, and recovery guidance. - [x] **DES-26 — Separate authentication-code verification from sign-in.** Show email and password on the initial screen. After successful password verification, show a dedicated authentication-code step only when the server requires it, with Verify and Back to sign in actions, clear instructions and accessible error/pending feedback. This is additional verification, not passwordless code login. **Done when:** ordinary sign-in, required-code sign-in, incorrect/expired/replayed codes, retry limits and back/restart behavior pass UI and direct API checks; no protected session exists while required verification is pending. **Owner:** Frontend/Backend/QA. **Dependencies:** DES-09, DES-20. **Recorded:** local sign-in has no code field and entered the app. `test_cloud_admin_requires_totp` checks the challenge, a wrong code, a valid code, replay, cancel, expiry, and the retry limit. ## Execution rules

- All tasks start open. Record evidence before marking acceptance complete; role labels are responsibilities, not assigned individuals.
- Implement one coherent reference journey before changing every screen. Do not treat cosmetic changes alone as workflow completion.
- Preserve current work, canonical identities, enrollment history, audit records, access boundaries, assessment policies and existing links.
- Prefer shared components and style tokens over local visual fixes; do not introduce a second competing pattern.
- This backlog reorganizes and improves existing capabilities. New fees, attendance, payroll or portal modules need separate requirements.
